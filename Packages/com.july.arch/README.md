# July Arch

July Arch 用少量明确角色组织模块边界。简单模块可以只使用这些角色；复杂模块仍然沿用相同边界，再通过普通类拆分模块内部逻辑，不为复杂度继续增加框架角色。

## 基本角色

| 角色 | 职责 |
| --- | --- |
| `System` | 提供模块能力，编排一次业务操作，协调 Store、普通逻辑类以及其他模块 |
| `Store` | 持有模块运行期间的业务事实和可变数据，并向外提供观察入口 |
| `Procedure` | 编排包含动画、等待、广告等异步环节的一次业务流程 |
| `View` | 处理显示和输入，将用户意图提交给 System 或 Procedure |

System 不直接持有或调用 View。业务流程若需要等待表现完成，由 Procedure 协调。

## 复杂模块的归属判断

遇到一段代码时，依次判断：

1. 它是不是模块运行期间需要保留、查询或观察的业务事实？是则放入 Store 及其数据对象。
2. 它是不是只维护一个数据对象自身的不变量？是则由该数据对象负责。
3. 它是不是显示，或者把输入转换成用户意图？是则属于 View。
4. 它是不是包含业务步骤与动画、等待或外部异步行为的顺序协调？是则使用 Procedure。
5. 它是不是一段内聚、可独立命名，并具有明确输入和输出的复杂计算？是则拆为 System 使用的普通逻辑类。
6. 剩下的代码是否在决定一次模块操作如何开始、推进、提交，或者需要协调其他模块？是则由 System 负责。

一段代码同时命中多个问题时，应先拆开其中不同的职责，再分别归属。这些判断不要求固定的类数量和目录层级。

## System

System 负责模块的主要业务操作，但“主要”指掌握用例入口、执行顺序和提交结果，而不是必须包含最多代码或所有算法。

System 可以：

- 读取和修改 Store；
- 持有并调用普通逻辑类；
- 调用其他模块能力；
- 管理只与执行过程有关的生命周期资源，例如时钟、取消和完成信号；
- 决定一次操作何时开始、推进、提交和结束。

System 不应：

- 再保存一份已经属于 Store 的业务数据；
- 直接持有或调用 View；
- 因为文件变长就机械地把每个步骤拆成一个类。

## Store 与数据对象

只要数据会影响后续业务判断，并需要跨越一次局部调用继续存在，它通常就是 Store 中的业务事实。格子、订单、战斗单位、冷却、当前轮次等数据都属于这一类，而不是 System 的私有缓存。

默认先使用一个 Store。只有出现明确且独立的生命周期、订阅范围或性能边界时，才考虑拆分多个 Store；不能仅因字段较多而拆分。

是否序列化与是否属于 Store 是两个问题。Store 可以只保存本轮运行时数据；需要存档的数据再通过对应的序列化能力处理。

数据对象可以维护自身的局部不变量和变化，例如：

- 一个格子改变占用状态；
- 一个敌人承受伤害；
- 一个冷却计时并判断自身是否完成。

跨多个对象的选择、组合、分配和模拟不应塞进某个数据对象，应由 System 或普通逻辑类负责。

数据命名应表达业务含义，例如 `Round`、`Board`、`BattleRun`。不要用宽泛的 `State` 把不同性质的数据混在一起。

## 普通逻辑类

当 System 中出现一段内聚的复杂逻辑，并且能够说清楚它接收什么、产出什么时，可以将其拆为普通类。普通类是模块内部实现，不是 July Arch 的新角色。

命名应直接暴露职责。常见但不封闭的命名包括：

- `Generator`：生成一组满足约束的数据；
- `Resolver`：根据已有事实推导或分配结果；
- `Selector`：从候选对象中做选择；
- `Calculator`：完成纯计算；
- `Validator`：验证来自责任边界的数据或配置；
- `Simulator`：按既定顺序推进一套连续模拟。

避免使用无法说明职责的 `Helper`、`Logic`、`Manager`。也不把 `Engine`、`Rule`、`Strategy` 规定成复杂模块必须具有的层级。

一个普通类可以较深、包含多个紧密相关步骤。判断是否继续拆分时，看新类能否隐藏一项独立复杂度，而不是看文件行数。如果拆分后只是多了一层转发或必须来回阅读多个类，拆分没有产生价值。

## Procedure 与事件

Procedure 和事件解决的问题不同：

- 一次操作存在明确的异步先后顺序，并需要等待表现或外部行为时，由 Procedure 协调；
- 同一个事实变化需要被多个互不依赖的对象监听，或者需要持续广播时，使用事件。

只有单一异步流程时，不需要为了“解耦”额外发送事件；存在界面、音频等多个独立监听者时，事件则是合理边界。

Procedure 只在需要时携带供表现使用的最小信息。不要为每个步骤制造一套 Result 类型，也不要让 View 反过来查询和重建刚刚完成的业务计算。

## 验证与失败策略

采用“边界验证、内部信任、违约快速失败”：

- 用户输入、配置、存档、网络和第三方数据在进入责任边界时验证一次；
- 下游代码依赖已经建立的契约，不重复验证或重复查询同一结论；
- 内部不变量被破坏时应明确失败，不用默认值、静默返回或伪造成功掩盖问题。

一次计算得到的候选集合或判定结果，应沿调用链显式传递，避免下游逐项重复进行同样的筛选和验证。

## 适用边界

本指引不规定：

- 一个复杂模块必须有多少个类；
- 固定的目录结构；
- 必须使用某个普通类后缀；
- 一个模块永远只能有一个 Store；
- 必须照搬某个游戏模块的实现结构。

它只提供一套稳定的职责判断顺序。离散的回合玩法和连续的战斗模拟可以有不同内部形态，但都应遵守相同的数据归属、交互边界和拆分原则。
